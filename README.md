## Быстрый старт

Нужен Docker с Docker Compose и запущенным Docker Engine (например, Docker Desktop в режиме Linux containers). Локальные Node.js и PostgreSQL для этого сценария не нужны. Из корня проекта:

```sh
docker compose up --build
```

После миграций и seed доступны:

- [http://localhost:3000/graphql](http://localhost:3000/graphql) — Apollo Sandbox с полным запросом и переменной `slug: "denis-mozhayskiy"`: достаточно нажать Run.
- [http://localhost:3000/health](http://localhost:3000/health) — HTTP 200, `{"status":"ok"}` при доступной БД. Проверяет соединение через `SELECT 1`; при ошибке возвращает 503 без деталей подключения.

Для запуска в фоне:

```sh
docker compose up --build -d
docker compose logs app
```

Compose работает без `.env`. Хост-порты задаются переменными `DB_HOST_PORT` (по умолчанию 5432, только localhost) и `APP_HOST_PORT` (3000) в окружении или корневом `.env`. Например, значения `DB_HOST_PORT=55432` и `APP_HOST_PORT=33000` дадут Sandbox на `http://localhost:33000/graphql`. Порты внутри контейнеров остаются 5432 и 3000. При смене порта БД для локального Node.js нужно также исправить порт в `DATABASE_URL`.

Остановка с сохранением данных:

```sh
docker compose down
```

Полный сброс локальных данных (удаляет volume PostgreSQL; следующий запуск заново применит миграции и seed):

```sh
docker compose down -v
```

## Пример запроса

Полный вложенный запрос, с компактной записью полей:

```graphql
query FullProfile($slug: String!) {
  profile(slug: $slug) {
    id slug fullName headline summary location workFormat
    links { id kind label url }
    skills { id name category details }
    experiences {
      id company position startDate endDate isCurrent
      achievements { id text }
    }
    projects { id name description url repositoryUrl isRepositoryPrivate technologies }
  }
}
```

Variables:

```json
{ "slug": "denis-mozhayskiy" }
```

Фильтр навыков и алиасы в одном запросе:

```graphql
{
  profile(slug: "denis-mozhayskiy") {
    all: skills { name category }
    development: skills(category: DEVELOPMENT) { name details }
    quality: skills(category: QUALITY_AUTOMATION) { name }
  }
}
```

Доступны категории `DEVELOPMENT`, `INTEGRATIONS_OPERATIONS`, `QUALITY_AUTOMATION`. Без `category` или с `null` возвращаются все навыки. `profile` возвращает `null` для неизвестного slug; `profiles` — список профилей. Пустые связи возвращаются как `[]`.

## Локальная разработка

Нужны Node.js 24 (не ниже 24.15), npm 11+ и Docker для БД. Контейнер приложения должен быть остановлен, чтобы освободить порт 3000. Из корня проекта (в PowerShell вместо `cp` — `Copy-Item .env.example .env`):

```sh
docker compose up -d db
cp .env.example .env
npm ci
npm run db:deploy
npm run db:seed
npm run start:dev
```

Копирование `.env.example` перезаписывает локальный `.env`; при собственных настройках подготовьте его вручную. Если изменён `DB_HOST_PORT`, согласуйте с ним `DATABASE_URL` в `.env`. `db:deploy` применяет сохранённые миграции, `db:seed` собирает и запускает seed. Локальный `start:dev` работает с уже подготовленной базой; автоматический seed при каждом старте выполняется entrypoint контейнера.

Для SQL-логирования задайте `PRISMA_LOG_QUERIES=true` в `.env` и перезапустите приложение. Запросы и длительность пишутся только при `NODE_ENV=development`; параметры SQL в лог не выводятся. По умолчанию логирование выключено. Остановка локального сервера — Ctrl+C.

```sh
npm run build

```

Unit-тесты проверяют сортировки без изменения входных данных, форматирование дат и `isCurrent`, фильтрацию категорий, резолверы, порядок ключей и батчинг DataLoader, независимость кэшей запросов, ошибки БД, health и валидацию окружения.

Для e2e нужен работающий PostgreSQL и роль с правом создания БД (роль из Compose подходит). Соединение берётся из `TEST_DATABASE_URL`, затем `DATABASE_URL` из окружения/`.env`; без них используются локальные параметры Compose с учётом `DB_HOST_PORT`. E2e создаёт отдельную БД `candidate_e2e_<случайный суффикс>` со схемой `card`, выполняет `migrate deploy` и seed, после тестов удаляет БД. Так проверяется работа нестандартной схемы на всём пути CLI → seed → API; таблицы приложения в `public` отсутствуют. При аварийном завершении процесса очистка может не выполниться.

E2e проверяет все публичные поля seed, неизвестный slug, список профилей, пустые связи, алиасы категорий и кэши между HTTP-запросами. Через Prisma query events фиксируются ровно **6 SQL-запросов** для полного профиля: `profiles`, `profile_links`, `skills`, `experiences`, `projects`, `achievements`. Число остаётся 6 и для трёх профилей с 24 дополнительными местами работы; служебные запросы подготовки БД не входят в измерение. Также проверяются Sandbox, полный стандартный introspection с дополнительными метаданными, CSRF, отбрасывание чрезмерных алиасов и selections до SQL, невалидный slug без обращения к репозиторию, маскирование и логирование внутренних ошибок, 120 успешных запросов и HTTP 429 на 121-м, общий бюджет разных операций, игнорирование поддельного X-Forwarded-For при выключенном trust proxy и выбор последнего недоверенного IP при включённом.

## Архитектура и решения

### Границы слоёв

`resolver → service → repository → Prisma`. Резолвер разбирает GraphQL-аргументы и берёт DataLoader из контекста. Сервис содержит правила сортировки, представление дат, вычисление `isCurrent` и фильтрацию навыков; он ничего не знает о GraphQL, DataLoader и HTTP-контексте. Репозиторий выполняет запросы Prisma, включая методы загрузки по массивам родительских id. GraphQL-модели отделены от сгенерированных Prisma-моделей.

`DataLoaderFactory` в `src/graphql/` зависит от batch-методов сервисов. Для каждой операции создаётся новый набор загрузчиков в контексте HTTP-запроса; сервисы от фабрики не зависят. `PrismaModule` глобален, `PrismaService` управляет подключением и отключением. Health использует Prisma напрямую для проверки готовности БД.

### Загрузка связей и N+1

DataLoader объединяет обращения к одной связи по parent id: один SQL на батч связи на соответствующем уровне. Результаты группируются строго в порядке входных ключей, отсутствующие связи дают пустые списки. Для полного профиля это корневой запрос, четыре связи профиля и достижения опыта — 6 SQL независимо от числа родителей и повторений полей через алиасы. При запросе меньшего набора связей SQL будет меньше: константность относится к выбранному набору связей, а не ко всем возможным GraphQL-документам.

Альтернативы — заранее заданные Prisma `include` или построение `select` из GraphQL info. Первая схема может загружать лишние данные, вторая требует разбирать поля, фрагменты и алиасы и связывает план доступа к БД с устройством GraphQL-документа. Здесь выбран DataLoader: предсказуемое число запросов по запрошенным связям и уровням, независимость батчей от числа объектов и формы алиасов, простая проверка отсутствия N+1. Компромисс — несколько обращений к БД вместо одного запроса с JOIN; для небольшой визитки это несущественно.

`skills(category: ...)` фильтруется чистым методом сервиса **после** загрузки всех навыков профиля. Поэтому разные алиасы категорий используют общий батч и кэш, не меняя его содержимое. Кэш живёт только в текущем запросе.

В GraphQL нет обратных ссылок от Skill, Experience и Project к Profile: граф ацикличен. Глубина ограничена самой схемой (самая длинная цепочка — профиль → опыт → достижения), отдельный depth-limit не нужен. Это не ограничивает ширину документа или число алиасов.

### Модель данных

| Таблица | Назначение и ограничения |
| --- | --- |
| `profiles` | Профиль с UUID, уникальным slug, текстом и временными метками. |
| `profile_links` | Упорядоченные ссылки с enum типа, индекс по `profile_id`. |
| `skills` | Навыки с enum категории; уникальность `(profile_id, name)`, индекс `(profile_id, category)`. |
| `experiences` | Места работы, даты и порядок; индекс по `profile_id`. |
| `achievements` | Достижения с собственными id и порядком; индекс по `experience_id`. |
| `projects` | Проекты, необязательные описание/ссылки, признак приватного репозитория; индекс по `profile_id`. |

Achievement выделен в таблицу, поскольку достижение — отдельный упорядоченный объект с идентификатором и внешним ключом. `technologies` проекта — PostgreSQL `text[]`: это простой список строк без собственной сущности, атрибутов и справочника. Названия таблиц и колонок — snake_case через Prisma `@map`/`@@map`; в TypeScript используются camelCase. Внешние ключи настроены с `ON DELETE CASCADE`, включая достижения при удалении опыта. Индексы поддерживают выборки по родительским id; составной индекс навыков допускает выборку по его первому столбцу.

В БД даты опыта хранятся как `date` (первый день месяца), в API — строки `YYYY-MM`, что отражает точность исходного резюме и не навязывает клиенту часовой пояс. Форматирование использует UTC. `endDate: null` означает текущую работу, `isCurrent` вычисляется из этого признака. Текущий опыт идёт первым, затем по `startDate` убыванию и `sortOrder`; ссылки, навыки, проекты и достижения — по `sortOrder`.

### Seed и запуск

`prisma/seed/candidate.data.ts` — источник правды для содержимого визитки. Seed идемпотентен по содержимому: в одной транзакции делает upsert профиля по slug, удаляет его дочерние записи и создаёт их заново из файла. UUID профиля сохраняется; **id дочерних записей меняются при каждом seed**. Это осознанный компромисс ради простого обновления статических данных; внешним клиентам не следует сохранять эти id как постоянные ссылки. Ручные изменения данных профиля будут заменены следующим seed.

Dockerfile использует стадии зависимостей, сборки и runtime на Node.js 24 slim с OpenSSL. Runtime работает от непривилегированного пользователя `node`; содержит production-зависимости, Prisma CLI для миграций, скомпилированные приложение, клиент и seed. TS-исполнитель в runtime не нужен. Entrypoint выполняет `migrate deploy → seed → start`; ошибка подготовки останавливает запуск. Compose ждёт healthcheck PostgreSQL, healthcheck образа приложения вызывает `/health`. Сервер слушает `0.0.0.0`, обрабатывает завершение с отключением Prisma.

Prisma 7 подключается через driver adapter `@prisma/adapter-pg`. Конфигурация CLI и URL — в `prisma.config.ts`; клиент генерируется в `src/generated/prisma`, игнорируется Git и компилируется вместе с приложением. Генерация включена в `build` и pre-скрипты для lint, typecheck, тестов и локального запуска, поэтому чистая копия не требует ручной генерации. Версии зависимостей закреплены lock-файлом.

Общий `src/prisma/adapter.ts` используется приложением, seed и тестовыми клиентами. Он извлекает `?schema=` из URL и передаёт `{ schema }` вторым аргументом `PrismaPg`: сам pg этот параметр Prisma не применяет. Сигнатура проверена в установленном adapter-pg 7.10.1; подключение через адаптер описано в [документации Prisma 7](https://www.prisma.io/docs/orm/v7/core-concepts/supported-databases/postgresql). Без параметра используется `public`. Пул ограничен `DATABASE_POOL_MAX` (по умолчанию 5, допустимо 1–20), ожидание подключения — 5 секунд. Миграция одна — `init`.

### Защита публичного API

Небольшое собственное validation rule на `graphql` ограничивает каждую операцию **50 алиасами и 1000 selections**. Учитываются все поля, inline-фрагменты и каждое раскрытие именованного фрагмента, включая повторные spread; обработка прекращается при превышении бюджета. Это ограничение ширины документа, а не оценка числа строк в БД. Тяжёлая библиотека сложности для маленькой ацикличной схемы не нужна. Полный профиль и `profiles` со всеми полями проходят с большим запасом; пример категорий содержит 3 алиаса (расширенный e2e — 5), полный introspection со всеми опциональными метаданными — 240 selections. Отказ: HTTP 400, `GRAPHQL_VALIDATION_FAILED`, сообщение с названием и величиной лимита.

`@nestjs/throttler` хранит счётчик **120 запросов за 60 секунд на IP** в памяти одного инстанса. Адаптация выполнена в фабрике Apollo-контекста с `req/res`: один HTTP-запрос учитывается один раз до валидации и выполнения, включая introspection и повторное выполнение закэшированного документа. Это охватывает introspection, который не вызывает резолверы приложения. Ответ при превышении — HTTP 429, код `TOO_MANY_REQUESTS`, заголовок `Retry-After`: стандартный HTTP-статус понятен клиентам и мониторингу. Лимита достаточно для периодического polling Sandbox и ручных запросов. `/health` не ограничивается. Механизм хранения и работы с прокси описан в [документации Nest](https://docs.nestjs.com/security/rate-limiting).

`TRUST_PROXY=false` по умолчанию: X-Forwarded-For игнорируется. Допустимы также `loopback` (127.0.0.0/8, ::1) и `private` (loopback, RFC1918, IPv6 unique-local). Доверие всем адресам и число доверенных хопов не разрешены. Express выбирает последний недоверенный адрес справа в цепочке, поэтому произвольный левый IP не обходит счётчик. В production Compose используется `private`: соединение Caddy с контейнером может приходить с адреса Docker bridge.

Аргумент `slug` проверяется pipe до вызова сервиса/репозитория: `^[a-z0-9]+(?:-[a-z0-9]+)*$`, максимум 100 символов. Невалидный ввод получает `BAD_USER_INPUT`; корректный неизвестный slug — `null`. В production `formatError` заменяет неожиданные ошибки `INTERNAL_SERVER_ERROR` на `Internal server error`, удаляет внутренние extensions и пишет исходную ошибку со стеком через Nest Logger. Ожидаемые ошибки ввода и GraphQL-валидации сохраняют понятные сообщения; stacktrace в API отключён.

Sandbox и introspection намеренно включены в production: это публичное API визитки только для чтения, которое должен удобно проверить работодатель. Документ Sandbox и e2e используют общую константу `src/graphql/full-profile-query.ts`. CSRF-защита Apollo включена; Sandbox отправляет общий заголовок `Apollo-Require-Preflight: true`, в том числе для introspection. Интерфейс Sandbox загружается с CDN Apollo и требует доступа к нему.

## Деплой

Целевая схема: слабый VPS (1 vCPU), Docker Compose с приложением и PostgreSQL 17 Alpine, Caddy на хосте как reverse proxy с автоматическим HTTPS. Публичный адрес: [https://card.194-226-115-233.sslip.io/graphql](https://card.194-226-115-233.sslip.io/graphql). Образ содержит миграции и скомпилированный seed; entrypoint подготавливает БД при каждом старте. Роль БД должна иметь права на миграции и запись seed.

Образ собирается **локально**, чтобы сборка не расходовала память VPS. Команды ниже для POSIX shell (передача бинарного `docker save` через pipe в старом Windows PowerShell может повредить архив; там используйте `docker save -o card.tar`, `scp`, затем `docker load -i card.tar`):

```sh
docker build -t it-solutions-card:1.0.0 .
docker save it-solutions-card:1.0.0 | ssh user@vps 'docker load'
ssh user@vps 'mkdir -p ~/card/deploy'
scp docker-compose.prod.yml user@vps:~/card/
scp deploy/.env.prod.example user@vps:~/card/deploy/.env.example
```

На VPS из `~/card` скопируйте `deploy/.env.example` в `deploy/.env`, задайте случайный пароль в `POSTGRES_PASSWORD` и в `DATABASE_URL` (в URL пароль должен быть URL-encoded), согласуйте имя пользователя/БД и тег `APP_IMAGE`. Файл с секретами не коммитится. Production-файл самостоятельный, без `build` и без наложения dev Compose:

```sh
cp deploy/.env.example deploy/.env
chmod 600 deploy/.env
# Отредактируйте deploy/.env перед запуском.
docker compose -f docker-compose.prod.yml --env-file deploy/.env up -d
curl -f http://127.0.0.1:3200/health
docker compose -f docker-compose.prod.yml --env-file deploy/.env logs app
```

БД не публикует порт; приложение доступно только через `127.0.0.1:${APP_HOST_PORT:-3200}`. В Caddyfile на хосте укажите реальный домен (DNS A/AAAA должен вести на VPS; порты 80/443 доступны), затем перезагрузите Caddy:

```caddyfile
card.example.com {
    reverse_proxy 127.0.0.1:3200
}
```

Оба сервиса имеют `restart: unless-stopped`, healthchecks и ротацию Docker-логов 5 MB × 2 файла на сервис. Лимиты: app — 192 MiB и 0.60 CPU, db — 128 MiB и 0.40 CPU. V8 old-space ограничен 96 MiB, оставляя место нативной памяти, молодому поколению, Prisma и драйверу. PostgreSQL: `shared_buffers=16MB`, `max_connections=15`, `work_mem=1MB`, `maintenance_work_mem=16MB`, `effective_cache_size=64MB` (оценка планировщика), без параллельных query workers. Пул приложения — 5 соединений; остаётся резерв для миграций, healthcheck и администрирования. Это бюджет небольшого read-only API, а не настройки для массовых запросов.

Сумма жёстких потолков памяти — 320 MiB, они не являются резервированием; при примерно 300 MiB свободной RAM оба сервиса не смогут одновременно достичь потолков. Перед выкладкой проверьте реальный RSS и доступную память с учётом Docker/Caddy; небольшой swap полезен для пика запуска миграций. Обновление: перенести новый тег, изменить `APP_IMAGE`, повторить `up -d`. Остановка с сохранением БД: `docker compose -f docker-compose.prod.yml --env-file deploy/.env down`; `down -v` удаляет данные.

## Ограничения и возможные улучшения

- Seed при старте рассчитан на один запускаемый инстанс. Перед масштабированием миграции и seed стоит вынести в отдельный этап деплоя или защитить от конкурентного выполнения.
- Нет кэширования ответов между запросами. DataLoader устраняет повторные загрузки внутри одного запроса. Rate limit хранится в памяти одного процесса; при масштабировании потребуется общее хранилище счётчиков.
- Нет мутаций и авторизации: по заданию API предоставляет публичные данные только для чтения.
- `profiles` не имеет пагинации: данных мало; при росте списка она понадобится. Несколько SQL round-trip'ов можно пересмотреть при измеренной необходимости.
- Тесты проверяют наличие конфигурации Sandbox в HTML; доступность внешнего CDN и интерфейс Apollo зависят от сети проверяющего.
